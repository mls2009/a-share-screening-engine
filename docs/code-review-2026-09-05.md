# 代码审查与改进建议（2026-09-05）

## 第二轮实施更新

用户要求继续解决后，下列正确性问题已落实到代码：

- 周/月线完整性按交易日历判断；分钟合成要求组成K线完整且最终。旧非周期末特征读取时过滤、重建时清理。
- 周/月信号改用日线执行，节假日前信号在下一可用交易日09:30成交；分钟成交记录使用K线起始时间。
- 跨周期条件按左侧历史时点寻找已可用的右侧值，补足右侧历史；盘中不读取同日最终周/月收盘数据。
- 股票池使用上市、退市日期；资料不全提供提示。窗口条件支持 `comparison_operator`，标注同步使用该比较方式。
- 选股诊断按条件统计 true/false/unknown、缺失原因和数据日期，持久化并在页面展示；指标目录明确支持模式。
- 撮合涨跌停判断使用开盘价格，不再参考当根未来高低价；滑点越界拒单。复权限制价用对应未复权开盘比例换算，数据不足时报具体原因。
- 回测报告显示数据区间、状态覆盖、预热、未知信号、拒单；历史切片限定为条件所需窗口，T+1延后订单保留原信号时间。

## 已修复的问题

| 问题 | 原来的影响 | 修复后的行为 |
| --- | --- | --- |
| 数值条件接受字符串、数组、布尔值及非有限数 | 校验通过后发生比较异常，或产生无效结果 | 按单位校验常量类型；拦截非有限乘数及次数大于观察窗口的条件 |
| 排序字段指定但方向省略 | SQL 中出现 `None`，读取结果失败 | 默认升序，方向只生成受控 SQL 关键字 |
| 盘中整行复制昨日特征 | 昨日 MACD、RSI、形态等被当作今日指标 | 未重算的动态字段保持 unknown，仅保留身份元数据 |
| 快照叠加已同步的同日收盘数据 | 同一天被重复计入均线和涨跌幅 | 日线历史严格早于快照日期 |
| 实时量比覆盖 20 周期量比 | 相同条件在两种模式中使用不同定义 | 实时量比单独保留；20 周期量比沿用成交量除以20周期均量的公式 |
| 盘中均量条件未加载足够历史 | 均量无法正确计算 | 按均量窗口加载此前行情 |
| 当前快照混入其他筛选日期 | 过去日期看到未来行情，或当天使用过期快照 | 日期不一致的快照不参与计算，也不计入有效覆盖数 |
| 回测接受未计算的形态等指标 | 静默得到零交易，容易误认策略无信号 | 在请求校验阶段明确拒绝；同时检查左右指标 |
| 回测只有预热数据仍返回成功 | 空权益曲线、零收益伪装成有效回测 | 检查请求区间内存在最终 K 线，否则报缺少行情；非最终原始K线不参与派生 |
| 同时买入时重复用昨日价格估值 | 两只同走势股票各配50%，分别买入4166和3993股 | 以当前开盘估值冻结本轮仓位基准，两笔均为4166股 |

## 条件选股建议

1. **优先统一周期完成时间和跨周期对齐。** `FeatureBuilder.build_symbol` 直接聚合当前周、月，
   `MarketDataService.derive` 又统一标记 `is_final=True`。当前周/月尚未结束时，不能把这些值
   与已完成周期混用。建议为每个周期保存起止时间、实际可用时间和完成状态；跨周期比较按
   “当时已经可用的最后一条记录”匹配。现在 `evaluator._right_value` 按相同数组下标取左右值，
   日线的上一条和周线的上一条并不代表同一个可用时点。
2. **让用户看到数据缺失，而不只是零结果。** `ScreeningService.run` 目前只保留 true 的股票，
   false 与 unknown 都被排除。建议报告每个条件的命中数、未知数、缺失原因和数据日期，
   并为指标声明支持收盘、盘中、回测的能力。盘中暂不支持的指标应在界面说明，避免用户误解
   修复后匹配数下降。前后端也应通过明确的能力字段共享回测目录，替代“支持7个周期”的推断。
3. **历史选股使用当时的股票池。** 当前查询固定为 `where is_listed`，并读取当前证券名称、板块。
   建议按上市/退市日期建立历史股票池，并按日期读取状态；这也需要补齐历史数据源，不能仅修改
   一个查询就认为已消除幸存者偏差。
4. **补齐组合表达和排序入口。** 当前 `AT_LEAST/CONTINUOUS` 内部固定判断“大于”，建议后续允许
   对任意子条件做窗口计数，例如“最近10日中至少3日下跌超过阈值”。已有 `RankSpec`，可以把
   排序指标、方向和候选数量开放到 HTTP 与界面，明确入选后的排名依据。
5. **优化全市场查询前先测慢点。** `_enrich` 对每只股票、每条历史记录执行多次 SQL。
   优先统计含状态、形态、点位条件的耗时，再将这些关联读取改为批量查询；无需先重写数据库层。

## 回测建议

1. **最高优先级：拆开信号周期与成交时钟。** 目前周/月线以最后一个组成日作为时间戳，
   却以该周/月首日的开盘价成交，交易明细时间、状态检查日期和实际取价日期会不一致。
   建议周/月线仅用于形成信号，下一可交易日的日线或分钟线用于执行。未完成周期不得产生
   已确认信号。此项需要调整引擎时间模型，本次未把它当作局部修补完成。
2. **统一复权和交易约束的价格尺度。** 引擎直接比较 `bar.low/high` 与状态表的涨跌停价格，
   默认请求又使用前复权行情。若状态表采用未复权价格，比较会失真。建议用未复权价格撮合和
   检查约束，复权序列计算信号，并明确处理分红送转；同时记录状态数据覆盖率。
3. **完善成交模型与拒单可见性。** 当前“一字板”检查会读取本根K线的高低价来决定是否按开盘价
   成交，这些价格在开盘时尚不可知。建议改为明确的开盘限制规则，或下沉到更小周期模拟。
   再加入成交量参与上限、部分成交、撤单/重试策略、不同证券的委托单位与按日期生效的费用。
   现有 `rejected_orders` 已返回，前端应展示原因统计。
4. **报告研究稳定性。** 在已有收益、回撤、夏普、胜率之外，优先加入基准收益与超额收益、
   月度表现、换手率、持仓时间、未平仓盈亏，以及回测区间和指标预热覆盖情况。
   划分训练与样本外区间，做滚动验证和参数邻域检查，避免只挑历史最优参数。
5. **控制长历史回测的复制成本。** 引擎每根K线都会复制并反转从起点到当前的全部特征。
   可根据条件树所需 lookback 截取窗口，配合大规模分钟回测性能用例，保持信号结果一致。

建议实施顺序：周期与成交时钟 → 历史股票池及价格尺度 → 数据覆盖和拒单诊断 →
基准/样本外验证 → 排序表达与性能优化。
